# 公开高模与配件实测

日期：2026-09-10。环境：macOS ARM64、Minecraft 26.2、NeoForge 26.2，2K 档。

## 本次加入的模型

| 模型 | 原始三角面 | 2K 档选中模型三角面 |
| --- | ---: | ---: |
| Chassis Bolt Sniper | 68,188 | 40,428 |
| Marksman Rifle | 54,172 | 32,566 |
| Service Pistol，选用作者的 A 外形 | 16,650 | 13,158 |
| Vertical Grip，独立配件 | 8,428 | 7,564 |
| Suppressor，独立配件 | 9,840 | 8,912 |

前两把枪和配件来自 [3DAssets Mega Weapon Pack](https://3dassets.dev/packs/mega-weapon-pack)，手枪来自 [Poly Haven Service Pistol](https://polyhaven.com/a/service_pistol)。原始资产为 CC0。测试枪包还复用了 TacZ 的操作骨架和动画，因此本地测试包不能按全部 CC0 对外发布，具体来源见 [PROVENANCE](../gunpacks/public_mesh_showcase/PROVENANCE.md)。

这是单独的 `public_mesh_showcase` 枪包，没有覆盖默认枪包。挂点、尺寸、朝向和允许的配件类型都在枪包数据中设置，Java 渲染代码没有这些样本名称的专用分支。

## 游戏内结果

- 两把步枪均通过真实 Z 键打开改装界面，安装握把和消音器，再卸下。安装消耗背包配件，卸下返还；服务器数据与画面一致，装卸后无需重新加载资源包。
- 最新版本再次完成 Chassis 装卸；改装界面的握把分类使用完整枪械视图，不再因缺少分类视图而裁切。
- 三把枪与两件配件通过第一人称、地面和展示物品渲染；普通背包、创造背包和快捷栏使用模型生成的二维图标。角色预览和第三人称显示 mesh 枪身。
- 既有 AK47 与 mesh Bolt 均完成 8 倍瞄具的真实鼠标瞄准检查，镜框、场景和标线可见。这项检查使用已有 Bedrock 瞄具，不是新 mesh 玻璃材质测试。
- 手枪保留作者原有的 `LINEAR_MIPMAP_LINEAR` 采样设置；实机确认 2K 贴图有 12 层 mip，没有修改原始资产的采样参数来绕过加载。

## 性能和切档

| 场景，连续 60 秒 | 实测 |
| --- | --- |
| 2K 手枪 | 6,194 帧，每帧一次主体提交，无失败返回 |
| 2K Chassis + 两配件 | 6,105 帧，主体和两个配件每帧各提交一次 |
| 5 个展示物品 + 5 个地面物品 + 手持枪 | 平均 33.9 FPS，帧间隔 p95 为 32.478 ms；每帧 17 次模型提交 |
| 512 档改装界面预滚后复测 | 2,003 帧，主体和两个配件每帧各提交一次 |

十个展示物品由三把枪和两件配件各展示两次组成，不能当作十把不同的 8K 枪。当前结果证明多实例能渲染，并不代表大量高模已经达到流畅帧率。

2K -> 512 -> 2K 切换后，诊断中的旧尺寸纹理退出缓存。所测 glTF 纹理的逻辑容量由 184,549,536 字节降到 11,534,496 字节，再恢复到前者；同一资产的多个展示实例没有各自复制一套纹理。稳定时 CPU NativeImage 为零。这是本渲染器的纹理记账，不是整机内存或驱动显存读数。

切档使用真实资源加载进度，完成后回设置页。没有修改时的 903 个采样点均未出现加载界面。

一次较早的 512 改装捕获中，消音器少提交 117 帧，但没有失败返回；同条件预滚后未复现。原始记录保留，不把复测通过写成已经查明此前原因。

## 适配范围

本轮补的是共用的量化顶点、原生采样和 mip、mesh 配件加载、画质刷新及各渲染入口，不是只给某一把枪增加替换模型。模型仍需符合枪包的 glTF 格式与功能骨架约定。

不等于所有 mesh 都已支持。试选的玻璃瞄具使用尚未支持的 `KHR_materials_transmission`，未放进测试包；其他格式和扩展边界见 [渲染支持表](gltf-rendering.md)。

## 8K KTX2 回归

额外发现并修复了一条共用加载问题：合法的 8K KTX2 原图被强制转换为 PNG 后，体积反而超过单图限制。现在不缩小时保留压缩原图，只在首次上传时解码；真正降到 2K 时仍缓存 2K PNG，没有放宽原有安全限额。

用原有 Bolt Action Rifle 7.62 在最新版本实测：

| 项目 | 8K | 切回 2K |
| --- | ---: | ---: |
| 连续 60 秒主体提交 | 8,684 帧，每帧一次 | 9,909 帧，每帧一次 |
| 本渲染器 GPU 纹理逻辑容量 | 1,610,612,740 字节 | 117,440,516 字节 |
| 保留的编码贴图 | 6 张 KTX2，251,914,388 字节 | 9 张派生 PNG，95,357,577 字节 |
| 稳定窗口中的 libktx / NativeImage 对象 | 0 / 0 | 0 / 0 |

8K 稳定窗口的 61 个快照中，转码尝试次数固定为 6；再次切回 8K 才增加到 12，说明逐帧渲染没有重复解码。最终 2K 缓存中已无 8K 纹理。8K 重载的 1,094 个进度采样点记录了 0 到 1、成功完成并回到设置页；两次返回 2K 也成功。

这修好了加载失败和重复转换，不等于 8K 已经省内存。一次覆盖 2K 基线到 8K 的整进程采样为 8.67 GB 起始、11.42 GB 峰值、10.65 GB 结束；测试 JVM 固定使用 8 GiB 堆，数字还包含 Minecraft 和其他资源，不是单把枪或显存占用。上传复制阶段仍有短暂的双缓冲，不能把上表容量当作进程峰值。

最终标准构建通过 373 项测试，公开资产检查 10 项通过、1 项明确跳过不支持的玻璃扩展，枪包校验 54 项通过、运行时解析覆盖 43 个文件。测试探针未进入发布 JAR。游戏正常退出后，隔离存档的 56 个文件、选项和配置均与测试前逐项一致；最终保留均衡 2K，界面名称为“高”。本轮没有打开原始存档。
